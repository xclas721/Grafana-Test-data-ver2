## 2. 一句話認識本前端

Brainwave 前端是以 **Vue 3 + TypeScript + Vite** 為核心的 SPA 專案，目標是提供**清晰路由與版面、可重用組件與狀態、型別安全與主題／國際化**，與後端 API 對接後可完整支援登入、使用者／會員管理、系統設定與匯出等流程。

- **技術棧**：Vue 3（Composition API）、TypeScript、Vite、Pinia、Vue Router、Tailwind CSS v4、DaisyUI v5、Vue I18n、Luxon。
- **目錄概念**：`src/pages`（頁面）、`src/layouts`（PublicLayout／MainLayout）、`src/shared`（components、services、utils）、`src/stores`、`src/router`、`src/locales`。
- **設計重點**：雙軌登入（後台／會員）、Token 儲存可替換、API 透過 httpClient 統一帶 Bearer 與業務 headers、回應與錯誤處理與後端 Result 對齊、共用組件與工具庫、主題與 i18n 可切換。

## 3. 架構總覽

請求與畫面的典型流程：

1. **路由**：Vue Router 依 path 決定 Layout（PublicLayout 或 MainLayout）與頁面組件；`router.beforeEach` 檢查 `meta.requiresAuth`，未登入則導向 `/login` 或 `/front/login`，並可帶 `redirect` 查參。
2. **Layout**：公開頁（首頁、登入）使用 PublicLayout（Topbar + 主內容）；後台／前台需登入頁使用 MainLayout（側欄、麵包屑、主內容）或前台專用版面。
3. **API 呼叫**：頁面與 service 透過 `apiClient`（薄包裝）呼叫 `httpClient`；httpClient 依 path 以 `getAuthTokenStrategy()`／`getFrontTokenStrategy()` 取 token，帶入 `Authorization: Bearer`，並帶業務 headers（時區、語系等）；若後端回 200 且 body 為 `success: false`，會拋錯供頁面 catch 顯示 toast；4xx／5xx 由 httpClient 拋出，401 時清除 token 並導向登入頁。
4. **建置與型別**：`npm run build` 會先執行 `vue-tsc` 型別檢查；API 型別由 `npm run generate:api` 從後端 OpenAPI 產出 `src/api/generated/schema.d.ts`，與後端契約同步。

架構上再補充兩點：

- **錯誤頁**：401、404、500 有獨立路由與頁面，提供簡短說明與「返回首頁」「前往登入」等按鈕。
- **測試帳號**：登入頁與 README 提供測試帳號（如 `demo`／`123456`），與後端初始化帳號設定一致。

## 5. 各功能章節

### 5.1 路由與 Layout

採用靜態路由：公開區（首頁、登入）與需登入區（dashboard、users、members、system-configs、components、tools、examples、about）分屬不同 Layout；401／404／500 為獨立頁面。

**為什麼重要**：結構清楚、權限與版面一致，易於擴充新頁。

**名詞**：**PublicLayout**＝Topbar + 主內容，用於首頁與登入；**MainLayout**＝側欄 + 麵包屑 + 主內容，用於後台；**requiresAuth**＝route meta，為 true 時需登入。

**怎麼運作**：`router.beforeEach` 依 `requiresAuth` 與 store 的 `isAuthenticated` 決定是否導向登入頁；路徑 `/front/`\* 用 frontAuthStore，其餘用 authStore。錯誤頁路由為 `/401`、`/404`、`/500`，未匹配路徑導向 404。

**技術要點**：`src/router/index.ts`、`src/layouts/PublicLayout.vue`、`src/layouts/MainLayout.vue`。詳見 **README.md**、**專案樹狀架構.md**。

---

### 5.2 登入與 Token

後台登入（`/login`）與會員登入（`/front/login`）分開；登入成功後 token 寫入對應的 tokenStorage，後續 API 由 httpClient 自動帶 `Authorization: Bearer <token>`；401 時清除 token 並導向登入頁。

**為什麼重要**：雙軌身分與後端 Guard 對應，開發與上線行為一致。

**名詞**：**authStore**＝後台登入狀態與 token；**frontAuthStore**＝會員登入狀態與 token；**authService**＝呼叫後端 `/api/auth/login`、`/api/front/auth/login`。

**怎麼運作**：登入頁呼叫 authService，成功後以 store 的 setToken 寫入（實際寫入由 tokenStorage 策略決定）；Topbar 提供單一「登入」dropdown，展開為「後台登入」「會員登入」兩選項。受保護路由與 API 皆依 store 與 httpClient 的 token 判斷。

**技術要點**：authStore、frontAuthStore、authService、LoginPage、FrontLoginPage、Topbar。詳見 **README.md**、**docs/權杖儲存策略說明.md**。

---

### 5.3 Token 儲存策略

Token 不寫死在某個 storage，而是透過 `getAuthTokenStrategy()`／`getFrontTokenStrategy()` 取得實作（預設為 localStorage），可在 app 初始化時改為 sessionStorage 或自訂；httpClient 取 token 與清除 token 皆透過同一策略，與 store 一致。

**為什麼重要**：可依安全需求切換儲存方式，而不必改動多處程式。

**名詞**：**TokenStorageStrategy**＝get／set／remove 介面；**createLocalStorageStrategy**／**createSessionStorageStrategy**＝依 key 建立的實作；**setAuthTokenStrategy**／**setFrontTokenStrategy**＝替換策略（於 main.ts 初始化時呼叫）。

**怎麼運作**：authStore／frontAuthStore 登入時用策略的 set；httpClient 發請求時用策略的 get，401 時用策略的 remove。key 預設為 `auth_token`、`front_auth_token`。

**技術要點**：`src/shared/tokenStorage/`。詳見 **docs/權杖儲存策略說明.md**。

---

### 5.4 API 客戶端與錯誤處理

所有對後端的請求經由 `httpClient`（fetch 封裝），自動帶入 baseURL、Bearer token、業務 headers（時區、語系等）；若回應為 JSON 且 body 含 `success: false`，會拋錯；4xx／5xx 亦拋出 HttpError，401 時導向登入並清除 token。

**為什麼重要**：行為一致、錯誤可被頁面 catch 並以 toast 等方式呈現，與後端 Result 對齊。

**名詞**：**httpClient**＝request／get／post／put／delete；**apiClient**＝薄包裝，供 service 層呼叫；**ApiResult**＝與後端 Result 對應的型別（success、data、message 等）。

**怎麼運作**：service 呼叫 `apiClient.get/post/put/delete`，httpClient 組裝 URL、headers、body，發送後依 content-type 解析 JSON 或 text；若為 JSON 且 `success === false`，拋出含 message 的錯誤；若 status 非 2xx，拋出 HttpError 並視情況執行 401 導向。

**技術要點**：`src/shared/services/httpClient.ts`、`src/shared/services/apiClient.ts`、`src/shared/types/api.ts`。詳見 **README.md**、**docs/介面契約同步說明.md**。

---

### 5.5 API 契約與型別

後端提供 OpenAPI 規格（`/v3/api-docs`），前端以 `npm run generate:api` 產出 `src/api/generated/schema.d.ts`，供 service 與頁面使用，與後端介面同步。

**為什麼重要**：型別一致、減少手寫與不同步問題。

**名詞**：**schema.d.ts**＝openapi-typescript 產出的型別檔；**generate:api**＝腳本依後端 URL 取得規格並寫入上述檔案。

**怎麼運作**：需先啟動後端，再於前端執行 `npm run generate:api`；產出包含 paths、components.schemas 等，service 層可引用對應型別。

**技術要點**：`scripts/generate-api.mjs`、`src/api/generated/schema.d.ts`。詳見 **README.md**、**docs/介面契約同步說明.md**。

---

### 5.6 共用組件

按用途分為 base（Button、Card、Input、Modal、PageHeader 等）、form、data（DataTable、Pagination）、navigation（Breadcrumb、Topbar、TopbarControls）、feedback（TooltipWrapper、GlobalLoading 等），支援主題與 i18n。

**為什麼重要**：版面與互動一致、減少重複程式碼。

**名詞**：**shared/components**＝`src/shared/components` 下各子目錄；**DaisyUI**＝樣式與元件庫，與 Tailwind 搭配。

**怎麼運作**：頁面從 `@/shared/components` 引入所需組件；按鈕、輸入框等支援 variant、size、status 等；DataTable 支援 columns、data、loading、分頁、empty-text、actions 插槽。

**技術要點**：`src/shared/components/`（base、form、data、navigation、feedback）。詳見 **README.md**、**專案樹狀架構.md**；元件展示見後台「組件」區塊。

---

### 5.7 Store（狀態）

全域狀態由 Pinia 管理：auth（後台登入）、frontAuth（會員登入）、app（時區等）、theme（主題）、i18n（語系）、loading（全域載入狀態與訊息）。

**為什麼重要**：登入狀態、主題、語系等跨頁共用，與路由及 API 配合。

**名詞**：**Pinia**＝Vue 官方推薦的狀態庫；各 store 對應 `src/stores/*.ts`。

**怎麼運作**：authStore／frontAuthStore 存 token 與使用者資訊，登入／登出時更新；authStore 會解析 token role 並提供 `canEdit`、`canDelete` 供頁面做 RBAC 顯示控制；themeStore、i18nStore 與 UI 綁定；loadingStore 可由 httpClient 或頁面控制，用於全螢幕載入提示。

**技術要點**：`src/stores/auth.ts`、`frontAuth.ts`、`app.ts`、`theme.ts`、`i18n.ts`、`loading.ts`。詳見 **README.md**。

---

### 5.8 主題與國際化

支援多組 DaisyUI 主題（含自訂 brainwave），可切換；語系為繁體中文、英文，由 Vue I18n 與 locales 檔提供，可切換並持久化。

**為什麼重要**：展示與在地化需求常見，預先接好可複用。

**名詞**：**theme**＝DaisyUI 的 data-theme；**locales**＝`src/locales` 下語言檔；**i18nStore**＝當前語系與切換方法。

**怎麼運作**：主題與語系存在 store（必要時可持久化到 localStorage）；Layout 或 Topbar 提供切換入口；所有文案經 `t(key)` 取得。

**技術要點**：`src/stores/theme.ts`、`src/stores/i18n.ts`、`src/locales/`、DaisyUI 主題設定。詳見 **README.md**。

---

### 5.9 業務頁與 API 對接

後台具備使用者、會員、系統設定等列表與表單頁，與後端 REST API 對接；使用者頁提供「匯出 CSV」按鈕，呼叫 `GET /api/users/export` 並觸發下載。

**為什麼重要**：完整覆蓋從登入到 CRUD、匯出的流程，與後端能力對應。

**名詞**：**userService**、**memberService**、**systemConfigService**＝對應後端 `/api/users`、`/api/members`、`/api/system-configs`；**ApiResult**、**PageResponse**＝與後端 Result、分頁格式對齊。

**怎麼運作**：各頁載入時呼叫 service 的 search／getById 等；新增／編輯以表單送出後呼叫 create／update；錯誤由 catch 以 message 顯示。匯出 CSV 以 get 取得 blob 後建立下載連結。

**技術要點**：`src/shared/services/userService.ts`、`memberService.ts`、`systemConfigService.ts`；`src/pages/UserPage.vue`、`MemberPage.vue`、`SystemConfigPage.vue`。詳見 **README.md**、後端 **docs/本專案後台介紹.md**。

**檔案工具**：`src/shared/utils/file.ts` 提供 `base64ToFile`、`fileToBase64`（已於工具／檔案頁使用）與 `uploadFile`。`uploadFile` 預留給後端上傳 API，預期回應為 `success`／`code`／`message`／`data`（含 msgType、fileId）；目前後端尚無對應端點，專案內未呼叫，待後端提供後再對接即可。

### 5.10 環境變數與建置

以 `VITE_`\* 開頭的變數在 build 時注入，常用如 `VITE_API_BASE_URL`、`VITE_FRONTEND_PORT`、`VITE_BACKEND_API_TIMEOUT`、`VITE_PAGE_SIZE` 等；建置指令含 `npm run dev`、`npm run build`、`npm run type-check`、`npm run generate:api`。

**為什麼重要**：本地與部署環境可切換 API 位址與參數，型別與契約可重現。

**名詞**：**Vite**＝建置與 dev server；**vue-tsc**＝型別檢查；**generate:api**＝從後端 OpenAPI 產出型別。

**怎麼運作**：`.env` 或環境變數設定 `VITE_*`，程式以 `import.meta.env.VITE_...` 讀取；`npm run build` 會先 type-check 再 vite build；`generate:api` 需後端已啟動。

**技術要點**：`vite.config.*`、`README.md` 環境變數一節、`scripts/generate-api.mjs`。詳見 **README.md**、根目錄 **終端機操作指令.md**。

---

### 5.11 部署

前端為靜態資源，建置後可部署至任何靜態主機（如 Vercel、Nginx）；需設定 API 基址（如 `VITE_API_BASE_URL`）指向後端，並確認 CORS 與後端設定一致。

**為什麼重要**：與後端分離部署時，前端僅需正確 API 位址與靜態託管。

**名詞**：**dist**＝`npm run build` 產出目錄；**history 模式**＝Vue Router 使用 createWebHistory，部署時需讓未匹配路徑回傳 index.html（SPA 回退規則）。

**怎麼運作**：建置後將 dist 內容部署至 CDN 或主機；若使用 Vercel 等，通常內建 SPA 支援；後端需在 `app.cors.allowed-origins` 放行前端網域。

**技術要點**：README 建置與預覽、**docs/前端部署指南.md**、後端 **docs/後端部署指南.md**。
